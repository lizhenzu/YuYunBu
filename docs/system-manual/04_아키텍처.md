## 3. 계층 구조 — 두 세대가 섞여 있다

### 예전 방식 (1세대) — `Controller → BusinessLayer.Manage* → DataAccessLayer.Control* → Common.DataAccessModule`
- `Control*` 가 `StringBuilder` 로 SQL 문자열을 만들고(값을 문자열에 직접 넣음), `DataAccessModule.commonQuery/executeNonQuery` 가 실행한다.
- 결과는 `DataSet` → `DataSetExtensions.ToList<T>()` 로 모델에 담는다.
- **접속 문자열은 `DataAccessModule` 안에 하드코딩**되어 있고, `ConstatsCommon.timeDifference16 == 16` 이면 운영 DB, 아니면 로컬 DB로 붙는다. 즉 appsettings 와 무관하다(07 문서의 가장 큰 위험).
- 예: 기도문(BessingChild), 5분 말씀, 공과, 퀴즈 출제, 인사 정보, 성경 진도 일부.

### 새 방식 (2세대) — `Controller → Services.I*Service → (Repository) → SqlConnection / DbContext`
- `Startup.ConfigureServices` 에서 `AddScoped` 로 등록하고 생성자로 주입한다.
- 대부분 `SqlParameter` 를 쓴 파라미터 SQL 이고, 접속 문자열은 `IConfiguration.GetConnectionString("DefaultConnection")` 에서 읽는다.
- 예: 도전 성경말씀(`DailyMission2Service`), 선물(`StudentPointGiftService`), 출석(`AttendanceService`), 365 기도, 가족 사진, 주보, 앨범, 공지, 게시판.

### EF Core
- `ApplicationDbContext` — Identity 표(스키마 `Identity`: `User`, `Role`, `UserRoles` …).
- `AppDbContext` — 성경(`eBible*`, `UserBibleProgress`, `UserBookMark`, 요약 · 영상 · 검색 로그 · 허브 클릭 · 완독 로그), 완독 선물, 선물 품목, 가족 사진 콘테스트, 사람 정보 뷰(`view_UserCompositeInfo_2026`, 키 없음).
- `HanmadiDbContext` — 한마디 표(마이그레이션 사용).
- 나머지 대부분 표는 EF 모델이 없고 SQL 로만 다룬다. **마이그레이션으로 DB 전체를 만들 수 없다.** 표는 `SQL/` 스크립트 · 앱 시작 시 자동 생성 코드(`EnsureTable` 류) · 손으로 만든 것이 섞여 있다.

## 4. 요청 처리 순서 (미들웨어)

`Startup.Configure` 순서 그대로:

1. 예외 처리 — 개발: 상세 오류 / 운영: `/Home/Error` + HSTS
2. `UseHttpsRedirection`
3. **검색 엔진 · 도메인 처리**
   - `jamsilkids.com`(www 없음) GET → `https://www.jamsilkids.com` 으로 영구 이동
   - `/robots.txt` · `/sitemap.xml` 을 주소에 따라 직접 응답(공개 주소는 홈만 허용, 관리 경로 차단 / 운영 임시 주소는 전부 차단)
   - 공개 주소의 `/` 외 모든 응답에 `X-Robots-Tag: noindex, nofollow`
4. `UseStaticFiles` (wwwroot)
5. `UseCors("AllowAllOrigins")` — 모든 출처 허용
6. **로그인 · 가입 화면 처리** — 캐시 금지, 위조 방지 토큰 400 이면 `?stale=1` 로 같은 화면에 돌려보냄
7. **방문자 집계** `SiteVisitCounter.CountHomeEntry` — 하루 한 번 브라우저(쿠키 `jk_v`)를 센다
8. **옛 주소 이동** — `/DailyMission3/*` → `/DailyMission4/*`, `/StudentPointDashboard3/*` → `/StudentPointDashboard4/*` (GET · HEAD 만)
9. `UseRouting` → `UseSession` → `UseAuthentication` → `UseAuthorization`
10. 엔드포인트
    - `viewTeacherBooks/{id}` → `TeacherBooks/Index`
    - 기본 `{controller=Home}/{action=Index}/{id?}`
    - Razor Pages (Identity, Hanmadi)
    - SignalR `/hanmadi-hub`

그 다음 컨트롤러 단계에서:
- **전역 필터 `LogActionFilter`** — 컨트롤러 · 액션 · 사용자 · IP 를 `loginHistory` 에 비동기로 남긴다(`SharedComm.AddToLog`, 관리 계정 제외). 많은 컨트롤러에 `[LogActionFilter]` 가 또 붙어 있어 중복될 수 있다.
- **`BaseController.OnActionExecutionAsync`** — 세션에 사용자 정보(UserId · UserName · UserFullName · 부서)가 없으면 Identity 에서 채우고, 교회명 · 부서명(`CommonMetaData`: 잠실새내 · 유년부)을 세션과 ViewData 에 넣는다.

## 6. 캐시

`IMemoryCache` 를 홈 화면에 주로 쓴다(`HomeController`).
- 로그인 여부와 무관한 공통 값(오늘 말씀, 공지, 메뉴 정책, 생일 목록 등)을 짧게 캐시한다.
- **날짜가 바뀌면 달라지는 값은 키에 날짜를 붙인다**(예: `home:birthdays:v2:yyyyMMdd`, 10분).
- 생일을 고치면 `HomeCacheHelper.InvalidateBirthdays`, 가족팀이 바뀌면 `InvalidateFamilyMilestones` 로 바로 비운다.
- 완독자 목록 · 가족 마일스톤은 실시간성이 중요해 캐시하지 않는다.
- 성능: 홈은 여러 조회를 `Task.Run` 으로 병렬 실행한다. 그래서 `Program.cs` 에서 스레드풀 최소 스레드를 64로 올렸다(동기 ADO 호출이 스레드를 오래 잡기 때문).

## 7. 시간대

- 서버는 Windows(한국이 아닐 수 있음). **모든 날짜 · 시간은 `DateHelper.GetKoreaNow()` / `GetKoreaToday()` 로 구한다.** `DateTime.Now`, `DateTime.Today` 는 쓰지 않는다(팀 규칙).
- 한국 시간대 ID: Windows `Korea Standard Time`, 실패하면 `Asia/Seoul`.
- DB 쪽 일부 SQL 은 `GETDATE()`(DB 서버 시간)나 `DATEADD(HOUR, 9, SYSUTCDATETIME())` 를 쓴다 — 섞여 있으니 주의.
- "주일" 계산: `DateHelper.GetBaseSunday` (그 주 일요일).

## 10. 로깅 · 오류

- `DbLogger` 는 `dbo.Logs` 에 쓰도록 만들어져 있지만 **첫 줄에 `return;` 이 있어 꺼져 있다.**
- 접속 기록은 `loginHistory`(사용자별 마지막 1건).
- 많은 곳에서 오류를 `catch { }` 로 삼켜 화면이 비거나 0이 나온다(홈이 깨지지 않게 하려는 의도). 원인 추적이 어렵다.
- 표준 ASP.NET 로깅(Console)만 남는다. 운영 서버의 stdout 로그는 꺼져 있다(`stdoutLogEnabled=false`).
