# 07. 문제점과 개선 제안

> 중요도: 🔴 바로 고칠 것 · 🟠 새로 만들 때 반드시 바꿀 것 · 🟡 하면 좋은 것
> 비밀 값은 적지 않았다. 위치(파일 · 줄)만 적었다.

## 1. 보안

| 중요도 | 문제 | 위치 · 내용 | 제안 |
|---|---|---|---|
| 🔴 | **DB 접속 문자열(계정 · 비밀번호)이 소스에 있다** | `Common/DataAccessModule.cs` 13, 15줄(운영 · 로컬). Git 에 올라가 있다 | 즉시 DB 비밀번호 변경 → 코드는 `IConfiguration` 에서 읽게 → Git 기록에서 제거(BFG 등) |
| 🔴 | 기본 계정이 코드의 고정 비밀번호로 만들어진다 | `Data/ContextSeed.cs` | 시드 비밀번호를 설정값으로, 운영 계정 비밀번호 변경 |
| 🔴 | SQL 문자열 이어 붙이기 | `DataAccessLayer/Control*.cs` 대부분 (`StringBuilder` + 값 직접 삽입) | 모두 `SqlParameter` 로. 새로 만들 때는 EF Core 또는 Dapper |
| 🟠 | 쓰기 액션 일부에 로그인 · 권한 검사가 없다 | 아래 표 | 의도(익명 허용)인지 하나씩 확인 후 `[Authorize]` / 역할 지정 |

| 🟠 | CORS 모든 출처 허용 | `Startup` `AllowAllOrigins` | 쓰는 곳이 없으면 제거 |
| 🟠 | 권한이 역할 · 계정 이름 · 권한 글자(A/S/B) 세 방식으로 섞임 | `PrayManagerHelper`(계정 이름 Basic · SuperAdmin), `ManageUserInfo` 권한 글자, 역할 | 정책 기반 권한(`AddPolicy`) 하나로 통일, 계정 이름 예외 제거 |

## 2. 구조 · 코드

| 중요도 | 문제 | 제안 |
|---|---|---|
| 🟠 | **두 세대 계층이 공존**(Manage/Control + Services) — 같은 표를 두 방식으로 접근 | 서비스 계층 하나로. 도메인별 모듈(미션, 포인트, 성경, 기도, 소통, 사람) |
| 🟠 | 사람 키 3개(`UserName`/`UserId`/`PersonId`) 혼용 | 새 설계는 `PersonId`(정수) 하나를 모든 기록의 키로, 계정은 Person 에 1:1 연결 |
| 🟠 | 연도별 표(`_2025`, `_2026`)와 코드의 표 이름 하드코딩 | 표는 하나, `Year` 열 + 인덱스. 새해 작업이 사라진다 |
| 🟠 | 365개 화면이 `Layout = null`, CSS · JS 가 화면마다 복사 | 공통 레이아웃 + 디자인 시스템(색 · 버튼 · 카드 컴포넌트). 또는 프런트를 분리(SPA/모바일 앱) |
| 🟠 | 같은 기능의 세대별 컨트롤러 · 화면(DailyMission2/3/4, StudentPointDashboard3/4, Mission/Mission3 레이아웃) | 최신(4)만 남기고 정리, 옛 주소는 리다이렉트만 |
| 🟠 | 동기 ADO 호출을 `Task.Run` 으로 병렬화, 스레드풀 64 로 버팀 | 전부 `async` (`ExecuteReaderAsync`) |
| 🟡 | `catch { }` 로 오류를 삼킴 + `DbLogger` 꺼짐(`return;`) | 구조적 로깅(Serilog 등) + 오류는 기록하고 화면은 안전하게 |
| 🟡 | 세션이 메모리 저장 → 재시작 시 사라짐 | 세션 의존 제거(클레임에 이름 · 부서), 필요하면 SQL 세션 |
| 🟡 | 파일 이름에 공백 `Controllers/ChurchRecordController .cs` | 이름 수정 |
| 🟡 | `.bak_before_*`, `*.old`, 백업 폴더가 소스에 섞임 | Git 기록에 맡기고 삭제 |
| 🟡 | 철자 오류가 이름에 굳음(`Bessing`, `PraryBeginMesssage`, `ufn_UserFullMame`, `vierw_`, `Constats`, `Freind`, `EventMater`) | 새 설계에서 바로잡기 |
| 🟡 | 어셈블리 이름 `YunYunBu2024` | 프로젝트 이름과 맞추기(`web.config` 함께) |
| 🟡 | 테스트 코드 없음 | 점수 · 선물 금액 계산부터 단위 테스트 |

## 3. 기능 · 데이터

| 중요도 | 문제 | 제안 |
|---|---|---|
| 🟠 | 점수 규칙이 DB 함수 · C# · 화면 문구에 흩어짐 | 규칙을 한 곳(설정 표 + 서비스)에서, 화면은 그 값을 표시 |
| 🟠 | 하드코딩된 날짜 · 대상(여름성경학교 일정, 가족 사진 콘테스트 설정, 특정 받는 사람 아이디) | 행사 설정 표 + 관리 화면 |
| 🟠 | 외래 키 · 기본 키 없는 표 다수 | 새 스키마에서 FK · PK · 고유 인덱스(예: 하루 1회 기록 = `PersonId + 날짜 + 종류` 고유) |
| 🟡 | 백업 표 60개 이상, 큰 백업 표(`UserBibleProgress_20260725` 28만 행 등) | 파일 백업으로 옮기고 삭제 → DB 용량 확보 |
| 🟡 | 방문자 수가 실제보다 많음(쿠키 없는 요청 · 앱 내 브라우저 · 봇) | 로그인 사용자 기준 일일 활성 수(`loginHistory`)를 주 지표로 |
| 🟡 | `AdminBroadcast`(전체 알림) 화면이 실제로 보내지 않음 | 구현하거나 메뉴 제거 |
| 🟡 | 날짜 기준이 `GETDATE()`(DB 서버 시간)와 C# KST 로 섞임 | 모든 저장은 UTC, 표시만 KST, 또는 KST 를 앱에서 넘김 |
| 🟡 | 콘텐츠 개편이 SQL 스크립트 수작업 | 관리 화면에서 편집 + 이력 표 |

## 4. 새로 만든다면 — 설계 제안

### 4-1. 기술
- 백엔드: ASP.NET Core 9 Web API(또는 MVC 유지), EF Core 단일 접근, 비동기, 정책 기반 권한.
- 프런트: 모바일 우선. 두 선택지
  1. **Razor + 공통 레이아웃 + 컴포넌트**(지금 팀이 익숙, 서버 렌더링 유지)
  2. **SPA/PWA**(React · Vue) + API — 앱처럼 쓰는 사용 패턴(매일 미션)에 유리
- DB: SQL Server 유지, 마이그레이션으로 스키마 관리(EF Migrations 또는 DbUp), 시드 데이터 스크립트화.
- 설정 · 비밀: 환경 변수 / 호스팅 비밀 저장소. Git 에 비밀 0.
- 로깅 · 모니터링: Serilog + 파일/DB, 오류 알림.
- 배포: GitHub Actions → Web Deploy. 배포 전 빌드 · 테스트 자동.

### 4-2. 도메인 모델(핵심만)
```
Person(PersonId, 이름, 성별, 생일, 음력여부, 생일공개, 전화, 학교, 가족팀Id)
Account(AccountId, PersonId, 로그인ID, 역할)          ← Identity
Enrollment(PersonId, Year, 학년, 반, 구분[학생/교사/교역자/학부모])
Content(ContentId, 종류[말씀/기도/퀴즈/공과/365기도…], 공개일, 본문 JSON)
Activity(PersonId, ContentId, 종류, 날짜, 값, 점수)     ← 모든 미션 기록을 한 표로, 고유키 (PersonId, ContentId, 종류)
PointRule(종류, 점수, 하루한도, 허용기간일수)
PointLedger(PersonId, 날짜, 출처, 점수)                 ← 출석 · 묵상 · 전도 · 세계관도 여기에
Reward(단계, 금액) / RewardOrder(PersonId, 품목, 상태, 금액스냅샷, 처리자, 일시)
Product(품목, 가격, 이미지, 숨김)
Event(행사, 기간, 설정 JSON)
```
- 점수는 `PointLedger` 합계 하나로 계산 → 대시보드 · 선물 · 순위가 같은 값을 본다.
- 하루 · 주 단위 제한은 `PointRule` 로 설정.

### 4-3. 이전(마이그레이션) 순서 제안
1. 🔴 보안 3건(접속 문자열, 시드 비밀번호, SQL 파라미터화)을 지금 시스템에서 먼저 처리.
2. 데이터 정리: 백업 표 · 사용 안 하는 표 목록 확정(09 부록 B 의 행 수 참고).
3. 사람 키 통합 표(`UserName ↔ UserId ↔ PersonId`) 만들기.
4. 새 스키마로 데이터 이전 스크립트(클릭 기록 → Activity, 점수 → Ledger).
5. 화면은 사용 빈도 순(홈 → 도전 성경말씀 → 도토리 · 선물 → 성경 → 기도 → 나머지)으로 옮기기.
6. 한동안 옛 주소는 새 주소로 리다이렉트.

### 4-4. 꼭 지켜야 할 업무 규칙(이전 시 놓치기 쉬운 것)
- 미션은 오늘 · 어제 · 그제만 가능. 퀴즈는 2번까지. 친구 기도는 0점. 암송은 주 1회.
- 도토리 금액 표(100점 5,000원 … 2,000점), 사용 가능 = 받은 금액 − 구매 완료 · 숨김 주문.
- 가족팀 점수 합산과 단계(1000/3000/5000 상, 2000/4000 박수).
- 완독 선물 1~10독, 생일 선물 30일 전부터.
- 학생 판정 = 역할 코드 `T1001`.
- "Basic"·"SuperAdmin" 계정 이름 예외(기도 화면 관리) — 새 설계에서는 권한으로 대체.
- 모든 날짜는 한국 시간.
