> **확정된 결정 (2026-11-08)**
> - 삭제 범위: 6-1 의 **F(소통·사진)만 빼고 모두 삭제**. 출석 기록도 함께 삭제한다(막지 않음).

## 1. 목적

회원이 스스로 "탈퇴"를 요청하면 SuperAdmin 에게 알림이 가고, SuperAdmin 이 확인(승인)해야 계정과 사람 명부가 실제로 삭제된다.
회원이 즉시 지우지 못하게 해서 실수 · 장난 탈퇴를 막고, 출석 · 점수가 얽힌 사람은 SuperAdmin 이 판단한다.

## 3. 사용자 흐름

### 3-1. 회원 (본인)
1. `정보 관리`(`/HumanResource/ManageUserInfo`) 의 **내 정보** 묶음 맨 아래에 **탈퇴 요청** 줄이 있다 (빨간 글자).
   - **본인 화면에서만 보인다** (`UserId` 가 로그인한 본인일 때). SuperAdmin 이 남의 화면을 열었을 때는 숨긴다.
2. 누르면 **탈퇴 요청 화면** 으로 간다 — 되돌릴 수 없다는 안내, 사유(선택) 입력, 확인 문구 입력("탈퇴합니다"), `탈퇴 요청 보내기` 버튼.
3. 보내면 요청만 저장된다. 계정은 **그대로 로그인 · 사용 가능**. 정보 관리에는 "탈퇴 요청 중 (○월 ○일)" 표시와 **요청 취소** 버튼이 나온다.
4. 승인되면 계정이 사라진다 → 다음 접속부터 로그인이 안 된다. 반려되면 그대로 계속 쓴다.

### 3-2. SuperAdmin
1. 요청이 오면 **쪽지**가 온다 — "○○님이 탈퇴를 요청했어요" (모든 SuperAdmin 에게, 제목 한 줄 + 확인 화면 링크). 홈의 쪽지 안 읽은 개수에 잡힌다.
2. `정보 관리 › 사람 · 권한 › 탈퇴 요청 확인`(`/HumanResource/WithdrawRequests`, SuperAdmin 전용)에서 목록을 본다.
3. 줄마다 **승인(삭제)** · **반려** 버튼.
   - 승인: 확인 창("되돌릴 수 없어요") → 사람 데이터와 계정을 삭제 → 줄이 사라진다.
   - 반려: 요청만 닫는다. 회원은 계속 쓴다.

## 5. 데이터 — 새 표 `PersonWithdrawRequest` (첫 호출 때 자동 생성)

| 열 | 형식 | 설명 |
|---|---|---|
| Id | int identity PK | |
| UserId | nvarchar(450) | 요청한 계정 |
| UserName | nvarchar(256) | 로그인 아이디 |
| FullName | nvarchar(100) | 요청 당시 이름 (삭제 뒤에도 기록이 남게) |
| Reason | nvarchar(500) null | 사유(선택) |
| Status | nvarchar(10) | `PENDING` · `APPROVED` · `REJECTED` · `CANCELED` |
| InsertDT | datetime | 요청 시각 (한국 시간) |

| DecidedBy | nvarchar(256) null | 처리한 SuperAdmin |

- 계정 한 명당 `PENDING` 은 한 건만 (중복 요청 방지).
- 승인 뒤에도 요청 기록은 **남긴다**(누가 언제 승인했는지 감사용). 개인정보는 `FullName` · `UserName` 뿐이다.

## 6. 처리 규칙

**요청 (`POST /HumanResource/WithdrawRequest`)**
- 로그인한 본인만. 본인 `UserId` 로만 만든다 (남의 `UserId` 를 넘겨도 무시).
- SuperAdmin 계정은 탈퇴 요청 불가 ("관리자 계정은 직접 정리해 주세요").
- 이미 `PENDING` 이 있으면 새로 만들지 않고 안내만.
- 저장 후 모든 SuperAdmin 에게 쪽지 한 통씩 (`PopMessage`, 보낸 사람 = 요청자).

**취소 (`POST /HumanResource/WithdrawCancel`)** — 본인의 `PENDING` 만 `CANCELED` 로.

**승인 (`POST /HumanResource/WithdrawDecide`, SuperAdmin, `approve=true`)**
1. `PENDING` 인지 확인 (이미 처리됐으면 안내).
2. 방어: SuperAdmin 계정 금지 · 출석 기록 있으면 **막고** 이유 표시 (아래 7번 미결정).
3. **6-1 의 삭제 목록 전체**를 한 트랜잭션으로 삭제 (`DeletePersonDataAsync` 를 이 목록으로 넓힌다) → 성공하면 파일(프로필 · 사진)을 지우고 `UserManager.DeleteAsync` 로 계정 삭제.
4. 요청을 `APPROVED` · `DecidedDT` · `DecidedBy` 로 갱신.
- 순서는 **데이터 먼저, 계정 나중** — 중간에 실패해도 계정이 남아 다시 시도할 수 있다 (미배정 삭제와 같은 원칙).

**반려 (`approve=false`)** — `REJECTED` 로만 바꾼다. 회원에게는 쪽지로 알린다("탈퇴 요청이 반려됐어요").

**권한** — 요청 · 취소는 `[Authorize]`(로그인), 확인 · 승인 · 반려는 `[Authorize(Roles = SuperAdmin)]`. 서버에서 다시 확인하고, 화면 숨김에만 기대지 않는다.

### 구현 방식 (제안)
- 코드에 **삭제 목록(표 이름 · 열 이름 · 키 종류)을 한 곳에 모아** 두고, 승인 때 목록을 돌며 지운다. 표가 늘면 이 목록만 고친다.
- 이 문서의 표 목록은 **2026-10-21 기준**이다. 구현 전에 운영 DB 의 `INFORMATION_SCHEMA.COLUMNS` 에서 `UserName` · `UserId` · `PersonId` 열이 있는 표를 다시 뽑아 빠진 표가 없는지 대조한다.
- 승인 화면에 **삭제될 건수 미리보기**(표별 행 수)를 보여 준다 — "미션 기록 312건, 성경 진도 4,100건, 쪽지 12건 …". SuperAdmin 이 규모를 보고 승인한다.
- 존재하지 않는 표(만들기 전 환경)는 건너뛴다 (`OBJECT_ID` 확인).

## 7. 정해 주셔야 할 것 (미결정)

1. ~~삭제 범위~~ → **결정됨: 이 사람과 관련된 모든 정보를 삭제** (위 6-1 목록). 남은 확인: 6-1 의 "지우지 않는 것"과 "백업 표"를 이대로 둘지.
2. **출석 기록이 있는 사람.** 지금은 삭제를 막는다. 탈퇴 요청은 오히려 출석 기록이 있는 아이가 대부분일 것이다.
   - **A. 막는다** (SuperAdmin 이 직접 정리)
   - **B. 출석은 남기고 사람 명부만 이름을 가려 보관** (통계 유지, 구현이 늘어남)
   - **C. 출석 기록도 함께 지운다**
3. **가족팀 · 친구팀 구성원인 경우.** 팀장이 탈퇴하면 팀은 어떻게 하나 (팀 해산 / 다른 사람에게 넘김 / 승인을 막음).
4. **쪽지 알림 외에** 홈이나 정보 관리 상단에 "탈퇴 요청 N건" 배지도 둘까.
5. **사유 입력**을 필수로 할까, 선택으로 둘까 (설계는 선택).
6. **게시글 · 댓글** (`BoardAnonymous` · `BoardHelpDesk` 와 댓글): 탈퇴자가 쓴 글을 지울까, 글은 두고 작성자만 비울까. 다른 사람이 댓글을 단 글을 지우면 그 댓글도 사라진다.
7. **백업 표**에 남은 개인정보(`UserBibleProgress_20260725` 등)도 지울까 — 기본은 지우지 않는다.

## 8. 구현 순서 (확정 후)

1. `PersonWithdrawRequest` 표 · 데이터 접근 함수 (요청 · 취소 · 목록 · 처리).
2. 정보 관리 "탈퇴 요청" 줄 · 요청 작성 화면 · 대기 표시와 취소.
3. 쪽지 알림 (SuperAdmin 전원).
4. 탈퇴 요청 확인 화면 · 승인(삭제) · 반려.
5. 정보 관리 사람 · 권한에 "탈퇴 요청 확인" 메뉴 줄 추가.
6. 빌드 · 점검 — 테스트 계정으로 요청 → 쪽지 → 승인 → 로그인 불가까지 확인.

## 9. 위험과 방어

- **되돌릴 수 없는 삭제** → 승인 때만 삭제, 확인 창, 요청 기록은 남김.
- **남의 계정 삭제 요청** → 서버에서 로그인한 본인 `UserId` 로만 요청을 만든다.
- **SuperAdmin 오삭제** → 요청도 승인도 SuperAdmin 계정은 막는다.
- **운영 DB 직결** → 새 표는 첫 호출 때 자동 생성(기존 방식). 게시 후 처음 쓰는 순간 표가 하나 늘어난다.
- **쪽지 폭주** → 계정당 `PENDING` 한 건만 허용해서 반복 요청으로 쪽지가 쌓이지 않게 한다.

## 10. 확인(테스트) 시나리오

1. 일반 회원 화면에 "탈퇴 요청"이 보이고, SuperAdmin 이 남의 화면을 열면 안 보인다.
2. 요청 → SuperAdmin 쪽지 도착 → 확인 화면 목록에 나타난다.
3. 같은 회원이 다시 요청해도 새 건이 안 생긴다. 취소하면 목록에서 사라진다.
4. 승인 → 사람 명부 · 반 · 역할 · 계정이 사라지고 로그인이 안 된다. 요청 기록은 `APPROVED` 로 남는다.
5. 반려 → 회원은 계속 로그인되고 쪽지로 반려를 받는다.
6. 출석 기록이 있는 회원 승인 시 (7번 결정에 따라) 막히거나 처리된다.
7. 일반 회원이 `/HumanResource/WithdrawRequests` 주소를 직접 열면 접근이 거부된다.
